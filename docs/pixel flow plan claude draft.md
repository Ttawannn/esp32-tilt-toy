## 2. ขอบเขต

**ตัดสินแล้ว: ทำเป็นโหมดใหม่แยกจากโหมดน้ำเดิม ไม่แทนที่ FLIP**

- เพิ่มโหมดใหม่ `pixel-flow` (Pixel Flow / น้ำพิกเซล) **ต่อท้าย** โหมดเดิม เป็นโหมดที่ 9 (index 8) ไม่แตะโหมด `water`, `water-inertia`, `water-swirl` ที่ใช้ FLIP
- ตัวจำลอง (`pixel_flow.h` / `pixel-flow.js`) แยกไฟล์จาก `flip_fluid.h` / `fluid.js` ไม่แชร์โค้ด solver กัน ใช้ร่วมกันแค่ `waterForces()` สำหรับแรงโน้มถ่วง + แรงกระตุก และกฎหาผิวน้ำ
- โหมดใหม่มีตัวตนครบเหมือนโหมดอื่น: id ใน NVS, ลำดับกดปุ่ม BOOT, ตัวเลือกในหน้าตั้งค่าบนมือถือ, การ์ดโหมดใน preview บนเว็บ, แถวในตาราง README
- ใช้ได้ทั้ง 6 โปรไฟล์จอ × 3 บอร์ด (18 firmware) ใน preview บนเว็บ และหน้าตั้งค่าบนมือถือ
- ไม่มีข้อความหรือกรอบบนจอ ตามหลักเดิมของโปรเจกต์
- ไม่เปลี่ยน GPIO, ผังสาย หรือรายการบอร์ด

### 2.1 ทำไมเป็นโหมดใหม่ ไม่ใช่อัปเกรดโหมดน้ำเดิม

ทั้งสองแบบเก่งคนละด้าน ถ้าเอา Pixel Flow ไปแทน FLIP จะเสียโหมดน้ำวนและความสมจริงของแรงดันน้ำ ถ้าเอา FLIP มาทำให้ละเอียดแบบวิดีโอ C3/C6 จะคำนวณไม่ทัน

| | FLIP เดิม (`water` / `water-inertia` / `water-swirl`) | Pixel Flow ใหม่ (`pixel-flow`) |
| --- | --- | --- |
| วิธีจำลอง | อนุภาค ≤ 900 เม็ดบนกริด 20×20 แก้สมการแรงดันทุก step | 1 เม็ด = 1 ช่องบนจอ ≤ 1 900 เม็ด ตก/ไหลข้างตามกฎ และเก็บความเร็วของตัวเอง |
| การวาด | ความหนาแน่นจากกริด 20×20 ขยายเป็น ~34×34 ช่อง ช่องละ ~7 px | ตำแหน่งเม็ดคือช่องบนจอ 40×40 ช่อง เม็ด 5 px ร่องดำ 1 px |
| หน้าตา | ผิวน้ำมนเป็นก้อน สี 2 ระดับ | ผิวขั้นบันไดคม หยดเดี่ยวกระเซ็น สี 6–8 เฉดพร้อมประกาย |
| ความสมจริง | น้ำอัดตัวไม่ได้ มีคลื่น น้ำวน แรงเหวี่ยง | คลื่นและการพุ่งขึ้นผนังเป็นแบบประมาณ ไม่มีแรงดันจริง |
| แรงที่รับ | แรงโน้มถ่วง + แรงกระตุก + การหมุนรอบจอ | แรงโน้มถ่วง + แรงกระตุก (ไม่มีน้ำวน) |
| ปริมาณน้ำ | ใกล้เคียงคงที่ (ชดเชยด้วย density) | คงที่เป๊ะ |
| การคำนวณ | เลขทศนิยม หนักบน C3/C6 ที่ไม่มี FPU | เลขจำนวนเต็มทั้งหมด |
| การส่งภาพ | เต็มจอทุกเฟรม ~46 ms (20 fps) | เฉพาะช่องที่เปลี่ยน ~7–8 ms (เป้า 30 fps) |
| หน่วยความจำ | ~28 KB | ~27 KB |
| JS ↔ C++ | ตรงกันแค่ทีละ step | ตรงกันทุกช่องตลอดการรัน |

ตัวเลขเวลาส่งภาพ fps และหน่วยความจำของ Pixel Flow เป็นค่าประมาณจากการคำนวณ ต้องวัดจริงตามข้อ 8

## 3. ตัวจำลอง: particle-on-grid แบบเลขจำนวนเต็ม

ไฟล์ใหม่ `firmware/tilt_toy/pixel_flow.h` (class `PixelFlow`) และ mirror `web/pixel-flow.js` ที่ใช้สมการเดียวกันทุกบรรทัด

### 3.1 โครงสร้างข้อมูล (จองคงที่ ไม่ allocate ระหว่างรัน)

| ข้อมูล | ชนิด | ขนาดสูงสุด |
| --- | --- | --- |
| `cols`, `rows` | int | ≤ 64 × 64, รวม ≤ `MaxCells = 2048` |
| `grid[cell]` | `int16_t` (−1 = ว่าง, −2 = ผนัง/นอก mask, ≥0 = index เม็ด) | 4 KB |
| `px[p]`, `py[p]` | `uint8_t` ตำแหน่งช่อง | 2 × 1 900 B |
| `fx[p]`, `fy[p]` | `uint8_t` เศษตำแหน่ง Q8 | 2 × 1 900 B |
| `vx[p]`, `vy[p]` | `int16_t` ความเร็ว Q8 (256 = 1 ช่อง/step) | 2 × 3 800 B |
| `stamp[p]` | `uint8_t` กันขยับซ้ำใน step เดียว | 1 900 B |
| `shade[cell]`, `shown[cell]` | `uint8_t` เฉดสีที่จะวาด / ที่วาดไปแล้ว | 2 × 2 KB |

รวมประมาณ **27 KB** ใกล้เคียง FLIP (~28 KB) ถ้า free heap บน C3 ตึงเมื่อเปิด Wi-Fi ให้รวม storage ของ `FlipFluid` และ `PixelFlow` เป็น `union` เพราะเปิดทีละโหมด (ตัดสินหลังวัดจริงในข้อ 8)

`MaxParticles = 1900` พอสำหรับระดับน้ำ 90% ของ 2048 ช่อง

### 3.2 ขนาดช่องต่อโปรไฟล์จอ

`pitch` = ระยะห่างช่องรวมร่อง 1 px (เม็ดจริง = `pitch−1`)

| โปรไฟล์ | pitch | กริด | ช่องในภาชนะ |
| --- | --- | --- | --- |
| GMT130 / ST7789 240×240 | 6 | 40 × 40 | 1600 (หักมุมโค้ง ~1560) |
| GC9A01 กลม 240×240 | 6 | 40 × 40 | ~1250 (mask วงกลม) |
| TFT 80×160 แนวตั้ง | 4 | 20 × 40 | 800 |
| TFT 160×80 แนวนอน | 4 | 40 × 20 | 800 |
| OLED 128×64 | 2 | 64 × 32 | 2048 (เม็ด 1 px ร่อง 1 px แบบ dot-matrix) |

คำนวณจาก `scene->width()/height()` ใน `resetMode()` ไม่ hard-code ต่อ `DISPLAY_PROFILE` ยกเว้นการเลือก mask

### 3.3 Mask ภาชนะ

- `round` (GC9A01): ช่องที่จุดกึ่งกลางอยู่นอกวงกลมรัศมี `min(cols,rows)/2` = ผนัง
- `rounded` (จอเหลี่ยมทุกรุ่น): มุมโค้งรัศมี ~3 ช่อง ให้น้ำตรงมุมโค้งตามขอบจอแบบในวิดีโอ
- OLED: สี่เหลี่ยมเต็ม

เขียน mask ลง `grid` เป็น −2 ครั้งเดียวตอน `configure()`

### 3.4 หนึ่ง step (fixed 30 Hz, `Step = 1/30 s`)

แรงที่ใช้ = gravity + linear acceleration แบบเดียวกับ `water-inertia` (เรียก `waterForces(WaterInertia, …)` ใน `toy_modes.h` / `web/water-modes.js`) แล้วแปลงเป็น `gx, gy` หน่วย Q8 ช่อง/step² ด้วยค่าคงที่ `G_PIXEL` (เริ่มที่ ~0.30 ช่อง/step² แล้วปรับให้ความรู้สึกใกล้วิดีโอ)

1. **ลำดับการประมวลผล:** เลือกแกนหลักของแรงโน้มถ่วง (`|gx| > |gy|` ?) แล้วกวาดทีละแถว/คอลัมน์ **จากฝั่งล่าง (ตามแรง) ขึ้นบน** ในแต่ละแถวสลับซ้าย→ขวา / ขวา→ซ้ายทุก step เพื่อไม่ให้น้ำเอียงข้างใดข้างหนึ่ง
2. **เร่งความเร็ว:** `v += g` แล้วหน่วง `v -= v>>6` (≈ 0.984) และจำกัด `|v| ≤ 3 ช่อง/step`
3. **เคลื่อนที่:** สะสม `f += v` ได้จำนวนช่องที่ต้องเดิน เดินทีละช่องแบบ Bresenham ไปตามทิศ `v`
4. **ชน:** ถ้าช่องถัดไปไม่ว่าง ลองตามลำดับ
   1. ทแยงลงสองข้างเทียบกับแรงโน้มถ่วง (สุ่มข้างก่อนด้วย RNG แบบ deterministic)
   2. เลื่อนขนานผิว (ตั้งฉากกับแรง) สูงสุด `DISPERSION = 3` ช่อง ไปทางเดียวกับความเร็วแนวขนาน ถ้าความเร็วแนวขนานเป็น 0 ให้สุ่มข้าง ข้อนี้ทำให้ผิวน้ำราบ
   3. ถ้ายังติด ตัดความเร็วส่วนที่พุ่งเข้าสิ่งกีดขวางเป็น 0 และคูณส่วนขนานด้วย 7/8 (แรงเสียดทาน) — นี่คือที่มาของคลื่นและการพุ่งขึ้นผนัง
5. ตั้ง `stamp[p]` กันเม็ดเดียวกันขยับซ้ำเมื่อถูกกวาดถึงอีกครั้งใน step นั้น
6. **ความเร็วร่วมกลุ่ม (เลือกได้):** ทุก 2 step เฉลี่ยความเร็วของเม็ดกับเพื่อนบ้านที่ติดกัน 4 ทิศเบา ๆ (`v += (avg−v)>>3`) ให้น้ำไหลเป็นก้อนแทนที่จะเหมือนทราย เปิด/ปิดด้วย flag เพื่อเทียบภาพ

เลขทั้งหมดเป็น int16/int32 และ RNG เป็น xorshift32 ที่ seed ได้ จึงให้ C++ กับ JS ได้ผล **ตรงกันทุกบิต** (ต่างจาก FLIP ที่ตรงได้แค่ single step)

### 3.5 การโต้ตอบ

- **เขย่า** (`shake()` / `POST /api/shake`): เม็ดที่อยู่ใกล้ผิว (ภายใน 4 ช่องจากผิว) ได้ความเร็วสวนแรงโน้มถ่วง 1.5–3 ช่อง/step บวกค่าสุ่มด้านข้าง → เกิดหยดกระเด็นแล้วตกกลับ
- **ระดับน้ำ** (`fill` 10–90%): `reset(fill)` เติมเม็ดจากฝั่งล่างตามแรงโน้มถ่วงปัจจุบัน
- **ลากบน preview**: ผลักเม็ดในรัศมี 3 ช่องตามความเร็วนิ้ว (เทียบ `stir()` ของ FLIP)

## 4. การวาดภาพ

ไม่ใช้ `rasterize()` ของ FLIP เพราะตำแหน่งเม็ดคือช่องบนจออยู่แล้ว

1. คำนวณ `shade[cell]` ทุกช่อง
   - 0 = ว่าง (ดำ)
   - ผิวน้ำ (ช่องน้ำที่มีช่องว่างอยู่ฝั่งตรงข้ามแรง — ใช้กฎเพื่อนบ้านแบบเดียวกับ `FlipFluid::rasterize`) = เฉดสว่างสุด
   - เม็ดที่เร็ว (`|v|` > 1 ช่อง/step) = เฉดฟอง/สว่าง
   - เนื้อน้ำ = 3–4 เฉดไล่ตามความลึกจากผิว (0–4 ช่อง) บวก sparkle จาก `hash(i, j, frame>>3) & 3` ทำให้แต่ละเม็ดสว่างต่างกันเล็กน้อยแบบในวิดีโอ
2. พาเลต RGB565 คงที่ 8 สี โทน cyan (`#0AA8E6` ฐาน, `#7DE3FF` ผิว) ต่อยอดภายหลังให้เลือกพาเลตจากมือถือได้ (ข้อ 6)
3. OLED: เม็ดน้ำ = 1, ว่าง = 0 ไม่ใช้เฉด (sparkle ปิด)

## 5. ความลื่นของภาพ (สำคัญ)

ตอนนี้ `loop()` เรียก `renderGame()+present()` ทุก ≥ 50 ms และ `present()` ส่ง framebuffer 240×240×16 bit = 115 KB ซึ่งใช้ ~46 ms ที่ SPI 20 MHz วิดีโอลื่นกว่านี้ชัดเจน

### 5.1 ส่งเฉพาะช่องที่เปลี่ยน (TFT ทุกรุ่น)

- ในโหมด `pixel-flow` ข้าม `GFXcanvas16` แล้ววาดตรงลงจอ: เทียบ `shade[cell]` กับ `shown[cell]` ช่องที่ต่างกันเรียก `panel.startWrite(); panel.writeFillRect(x, y, pitch−1, pitch−1, color); … panel.endWrite();`
- ช่อง 5×5 ใช้ ~50 B ข้อมูล + ~11 B คำสั่ง address ถ้าเปลี่ยน 300 ช่อง/เฟรม ≈ 18 KB ≈ **7–8 ms** ที่ 20 MHz (เทียบกับ 46 ms)
- เข้าโหมดใหม่, เปลี่ยน rotation/inversion หรือ fill → ล้างจอและบังคับวาดทุกช่อง (`shown[] = 0xFF`)
- ขณะเปิด Wi-Fi ที่ต้องแสดงชื่อ AP/IP บนจอ ให้กลับไปใช้ framebuffer path เดิม (ไม่ต้องลื่นในช่วงนั้น)
- OLED ใช้ buffer ภายใน driver (1 KB) ส่งผ่าน I²C เหมือนเดิม

### 5.2 จังหวะเฟรม

- เปลี่ยนเงื่อนไข `now-lastFrame>=50` เป็นค่าตามโหมด: `pixel-flow` = 33 ms (30 fps) โหมดอื่นคง 50 ms
- 1 เฟรม = 1 step คงที่ (ใช้ accumulator แบบ FLIP กันเฟรมตก แต่จำกัดไม่เกิน 2 step ต่อเฟรม)
- IMU อ่านจาก FIFO อยู่แล้วใน `main` จึงไม่ขาดข้อมูลระหว่างส่งภาพ

### 5.3 ทางเสริม (ทดลองบนจอจริงเท่านั้น)

- ลอง `setSPISpeed(40000000)` แยกต่อโปรไฟล์ ถ้าภาพไม่เพี้ยนให้เก็บผลไว้ใน `HARDWARE.md` (ใช้ได้กับทุกโหมด)

## 7. Tests

ไฟล์ใหม่ `tests/pixel-flow.test.mjs`

1. **อนุรักษ์มวล:** หลัง 600 step ด้วยแรงสุ่มและเขย่า จำนวนเม็ดเท่าเดิม ไม่มีสองเม็ดในช่องเดียว (`grid` กับ `px/py` สอดคล้องกัน) และไม่มีเม็ดอยู่นอก mask
2. **นิ่งแล้วราบ:** แรงลงล่าง 300 step → ความสูงคอลัมน์ต่างกันไม่เกิน 1 ช่อง, แถวล่างสุดเต็ม, เม็ดผิวน้ำได้ shade ผิว
3. **ตามการเอียง:** แรงไปขวา → ครึ่งขวามีน้ำ > 80% ครึ่งซ้ายว่าง
4. **โมเมนตัม:** หมุนแรงจากลงล่างเป็นไปขวาทันที → ภายใน 10 step มีเม็ดที่สูงกว่าระดับนิ่งบนผนังขวา (น้ำพุ่งขึ้นผนัง) แล้วกลับมาราบภายใน 200 step
5. **เขย่า:** หลัง `shake()` มีเม็ดลอยไม่ติดเพื่อนบ้านอย่างน้อย 5 เม็ด และนิ่งกลับภายใน 150 step
6. **mask:** วงกลมและมุมโค้งไม่มีน้ำในช่องผนัง ทุกโปรไฟล์ใน `profiles` ได้กริด ≤ `MaxCells`
7. **ระดับน้ำ:** `fill` 10/50/90 → สัดส่วนเม็ดต่อช่องในภาชนะคลาดไม่เกิน ±1%
8. **โหมด:** `modes.length === 9`, `pixel-flow` อยู่ท้ายสุด, `usesFill` ครอบคลุม 4 โหมด, ลำดับปุ่ม BOOT วนครบ 9 โหมด (แก้ assert `modes.length,8` ใน `tests/water-modes.test.mjs`)

C++ parity: `tests/motion/pixel_flow_parity.cpp` คอมไพล์ `pixel_flow.h` ด้วย host compiler (`CXX`) แบบเดียวกับ `state_parity.cpp` รัน 500 step ด้วย seed และลำดับแรงเดียวกับ JS แล้วเทียบ `grid` **ต้องตรงกันทุกช่อง**

ตรวจเพิ่มใน `tests/device.test.mjs`: หน้าตั้งค่ามี option `pixel-flow`, `/api/config` รับค่าได้ และ `tests/releases.test.mjs` ยังเป็น 18 artifacts version 0.1.4

## 8. Build, release และทดสอบบนเครื่องจริง

1. `npm test` ผ่านทั้งหมด
2. `npm run firmware` สร้าง 18 merged binaries ใหม่ ทุก manifest คง `hardwareTested: false` จนกว่าจะทดสอบจริง
3. `npm run build` แล้วลอง preview ทุกโปรไฟล์ใน `npm run dev`
4. Checklist บนเครื่อง (บันทึกลง `HARDWARE.md`)
   - `simMs` ของ `pixel-flow` บน ESP32 / C3 / C6 ที่ fill 50% และ 90% — เป้า < 8 ms (C6 ไม่มี FPU แต่โหมดนี้ไม่ใช้ float ในลูปหลัก)
   - `fps` ≥ 28 บนจอ 240×240 ทั้ง ST7789 และ GC9A01 ขณะเขย่าแรง
   - `freeHeap` ขณะเปิด Wi-Fi บน C3 (ถ้า < 40 KB ให้ทำ union storage ตามข้อ 3.1)
   - ภาพไม่มีรอยค้างหลังสลับโหมด/หมุนจอ, เม็ดไม่ทะลุขอบมุมโค้ง
   - ลอง SPI 40 MHz ต่อโปรไฟล์ (ข้อ 5.3)
5. Commit แยกเป็นลำดับ: (a) `pixel_flow.h` + `pixel-flow.js` + tests, (b) เชื่อมโหมดเข้า firmware/เว็บ, (c) direct-draw + frame interval, (d) docs + version bump + rebuild 18 binaries

## 9. นอกขอบเขต (ทำทีหลังถ้าต้องการ)

- **จอ 240×280 มุมโค้ง (ST7789V2, 1.69")** แบบในวิดีโอ: เพิ่มโปรไฟล์ `tft-240x280-st7789` (`firmwareId 6`, offset แถว 20 px) → firmware เพิ่มเป็น 21 ชุด, ผังสายและภาพในเว็บ, กริด 40 × 46
- **ESP32-S3** และบอร์ดสำเร็จรูปที่มีจอ/IMU ในตัว: ต้องเพิ่มบอร์ด IMU QMI8658 และ partition ใหม่
- **Launcher แบบไอคอน + แถบสถานะ (เวลา/แบตเตอรี่/ชื่อผู้ใช้)**: ขัดกับหลัก "จอคือพื้นที่เล่นทั้งหมด ไม่มีข้อความ" และเครื่องเรามีแค่ปุ่ม BOOT ไม่มีจอสัมผัส
- พาเลตสีให้เลือกจากมือถือ (ฟ้า/เขียวมรกต/ลาวา) — โครงพาเลตในข้อ 4 รองรับไว้แล้ว เพิ่ม key `palette` ใน NVS ภายหลัง
